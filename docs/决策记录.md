# 决策记录（ADR）

> **写完就不再反复讨论**，除非有新证据。改技术选型必须追加新条目，不许改旧条目。
> 为什么留在 GitHub：① AI 接手任务时要读，避免把已定的事再议一遍；② 答辩要讲「当时为什么这么定」，需要版本留痕。
> 进度 / 分工 → **腾讯文档**（人读的不放这里）。

**模板**：

```markdown
### D-00x 决策标题（YYYY-MM-DD）
- **背景**：为什么要做这个决定
- **选项**：A / B / C 各自代价
- **决定**：选了哪个
- **理由**：一句话
- **影响**：谁要跟着改什么
- **可逆性**：可逆 / 不可逆（不可逆的必须四人一致同意）
- **参与人**：谁在场
```

## D-009 手机端路线改为自研原生 Android App（2026-10-13）

- **背景**：D-002 定的是「协议优先、客户端零开发」，手机侧用系统现成工具（iOS 快捷指令 / Android HTTP Shortcuts）零代码接入。本条推翻 D-002 的路线选择，改为自研原生 Android App。
- **为什么放弃 iOS**（三条硬事实，非偏好）：
  1. **iOS 拿不到「应用时长」**：必须走 Screen Time API，需 `com.apple.developer.family-controls` entitlement。Apple 官方明确非家长监护用途通常被拒；Distribution 签名的 entitlement 属 managed capability，需提交申请，**审核 4–8 周且不保证通过**，TestFlight 亦不可用。
  2. **无macOS 开发环境**：本项目开发环境为 Windows + WSL，Xcode 为 macOS 独占，无法构建 iOS 端。
  3. HealthKit 读步数本身可行（免费开发者账号 + 开发签名即可），但**只能拿到步数**，拿不到应用时长 —— 而应用时长是本次改动的目标之一。
- **选项**：A 双端原生 App（iOS + Android）｜B维持 D-002 零开发接入｜**C 只做 Android 原生 App，放弃 iOS**
- **决定**：**C**。自研 **Android 原生 App**（Kotlin + Health Connect），不再支持 iOS。
- **理由**：Android 侧无 Apple entitlement 审批门槛，且 Health Connect + UsageStatsManager 能同时提供步数与手机应用时长，正好补上 iOS 拿不到的那一半；单端也能把工期压到可承受范围。
- **影响**：
  - W11 产出物从「快捷指令模板」改为「Android App 工程 + 上报逻辑 + 真机验证记录」，主责仍为 **D**。
  - **接口零改动即可承载**：`POST /api/ingest/health` 的 `steps` 字段直接复用，仅`source` 枚举需新增 `android-app`。
  - `phone` 快照需**新增** `screen_minutes` / `top_apps` 字段（只增不改，符合 Git 纪律第3 条）。
  - 新增 Android 工具链前置条件：JDK 17（本机已装 Android SDK，但**未装 JDK**）。
  - **W10 与 W11 的语义不可合并**：电脑侧是「实时前台应用 + session_sec」，手机侧是「区间累计分钟」，详见接口协议 §3.6。
- **风险**：
  - 需至少 1 台 **Android 真机**（模拟器无计步传感器，Health Connect 取不到真实数据）。
  - Android 13 及以下需用户另装 Health Connect APK；14+ 系统内置。
  - 后台读取需 `READ_HEALTH_DATA_IN_BACKGROUND` + WorkManager 周期任务（官方示例 1 小时一次），先探测 `FEATURE_READ_HEALTH_DATA_IN_BACKGROUND`，不可用则降级为前台读。
  - 「手机应用时长」用 `UsageStatsManager` + `PACKAGE_USAGE_STATS`（系统级特殊权限，须引导用户手动开启）；最小有效窗口 60 秒，Android R+ 锁屏返回 `null` → **拿不到实时的「当前前台 App」**，只能拿区间累计值。
  - **语言栈风险**：D 现有技能为 Python + pywin32，Kotlin 为新增栈，需评估学习成本（待确认）。
- **可逆性**：可逆（接口层只增字段；App 侧若卡壳可退回 D-002 的零开发接入，接口不动）。
- **参与人**：张鹏（A）决定，待B、C、D 追认。

## D-010 姿态估计采用 MediaPipe 1.x Tasks API（2026-09-23）

> 编号说明：本决策形成于 2026-09-23 团队会议；合入时（2026-10-23）发现编号与 D-009（手机端路线，2026-10-13）撞号，改为 **D-010**。决策内容未变，仅改编号。

- **背景**：`requirements.txt` 原先写 `mediapipe>=0.10.14`，实际安装取到 **1.0.1**；而 MediaPipe 1.0 **移除了旧的 `mp.solutions.*`（Solutions API）**，`vision/pose_estimator.py` 里的 `mp.solutions.pose` 直接抛 `AttributeError`，被外层 `except Exception` 吞掉后**静默降级**为"永远无人"——真机姿态链失效且不报错（M1-1/1-2/1-3 全废，现场极难查）。
- **选项**：A 钉回 `mediapipe<1.0`（旧 API，代码零改动，但 0.10.x 无 Python 3.13 轮子且不再更新）｜B 迁移到 1.x **Tasks API**（`PoseLandmarker`，需 `.task` 模型文件）｜C 换用其它姿态方案
- **决定**：**B**。依据 2026-09-23 团队会议「暂时使用最新版 mediapipe」。
- **理由**：新版能力完整（`PoseLandmarker` 输出同样的 33 点归一化坐标 + `visibility`，索引与 BlazePose 一致），是上游主推方向；迁移面仅 **1 个文件**（`infer()` 契约不变，`compute_metrics` / 规则 / 状态机 / Hub 零改动）；避免被 0.10.x 版本冻结绑死。
- **影响**：
  - `requirements.txt`：`mediapipe>=0.10.14` → **`mediapipe>=1.0`**；
  - 新增模型资产 `backend/models/pose_landmarker_lite.task`（约 5.5 MB，**提交进仓库**，保证 M4-5「干净机器从零跑」不依赖临时下载）；
  - `config.yaml` 新增 `vision:` 节（模型路径 / `num_poses` / 检测与跟踪置信度可配 → 服务 M2-2「改配置不改代码」）；`config.py` 增加 4 个对应字段；
  - `pose_estimator.py` 整体重写；**不再静默降级**：依赖缺失 / 模型缺失 / 路径错误一律 `ok=False` + 可读 `last_error`，并由采集线程推 `error` 帧；
  - `camera.py`：`_BaseThread._handle` 改名为 **`_on_observation`** —— Python 3.13 的 `threading.Thread.__init__` 会设置实例属性 `self._handle`（`_thread._ThreadHandle`），**遮蔽同名方法**，导致采集线程启动即崩（`TypeError: '_thread._ThreadHandle' object is not callable`）；
  - **模型必须以字节缓冲加载**：`BaseOptions(model_asset_buffer=...)`。mediapipe 的 C++ 层对**非 ASCII 路径**（本项目位于 `G:\中级实训\`）会报 `Unable to open file`，改用 buffer 可绕过；
  - **P4「是否引入 Git LFS」可以关闭：不需要** —— 5.5 MB 远低于 GitHub 单文件上限。
- **可逆性**：可逆。换回 0.10.x 只需把加载方式改回路径式 API；`infer()` 契约未变，上层不受影响。
- **验证**（本机 Python 3.13.7 / CPU / 无独显）：
  - `PoseEstimator.ok = True`，模型加载成功（`Created TensorFlow Lite XNNPACK delegate for CPU`）；
  - 空帧 → `person_present=False`；连续 60 帧无异常；单帧推理 ≈ **31.7 ms**（lite 模型，10 Hz 采样绰绰有余）；
  - `--sim` 起服后 WS 正常推送 `state`：`upright` → `away` → `slouch`（`neck_angle_deg=34.7`）；
  - 20 个 Python 文件语法检查 0 失败。
- **参与人**：四人（团队会议定方向，C 落地实现）。

## D-011 房间坐标与尺寸口径（2026-09-28）

> 编号说明：本两条决策形成于 2026-09-28；合入时（2026-10-23）发现原编号 D-009 / D-010 已被占用（D-009 手机端路线、D-010 MediaPipe Tasks API），分别顺延为 **D-011 / D-012**。决策内容未变，仅改编号。

- **背景**：XQ-008 搭 3D 房间时定了「1 单位 = 1 米、房间 6×6 m、后墙 z=-3、左墙 x=-3」这套口径，但只写在 `frontend/README.md` 与 `room.js` 头注释里，`docs/` 此前无任何空间坐标定义。B（家具）与 C（状态→场景映射）不一定会读前端 README，各按各的尺子写就会对不上。
- **选项**：A 各人自定（返工风险高）｜B 只留在 `frontend/README.md`（同上）｜C 进决策记录成文
- **决定**：**C**。房间空间口径如下，**任何人在房间里加东西都按这个来**：

  | 项 | 取值 |
  |---|---|
  | 单位 | **1 单位 = 1 米** |
  | 轴向 | y 轴朝上（Three.js 默认）；地面 `y = 0` |
  | 房间尺寸 | 6 m × 6 m；墙高 3 m |
  | 后墙 | `z = -3`（法线朝 +z） |
  | 左墙 | `x = -3`（法线朝 +x） |
  | 敞开的另两面 | `+z`、`+x` 不砌墙，给相机留机位 |

- **理由**：跨成员共用的空间口径必须有唯一真源，否则 M3 摆家具与做状态映射时会互相打架；决策记录是「AI 接手任务时要读」的文件，放这里命中率最高。
- **影响**：B（M3-1 家具）与 C（状态→场景映射）须按此口径；`frontend/README.md` 保留同一份口径作实现侧说明，**若两者冲突以本条为准**。
- **可逆性**：可逆，但已摆放的物体坐标要跟着改。
- **参与人**：A（张鹏）提出，待 B、C 追认。

## D-012 审核流程精简：取消强制第二人签字（2026-09-28）

- **背景**：原 `docs/README.md` §二 第 1 条要求每个 PR「至少 1 人 approval，写码人不能自评」。四人小组下每条改动都要凑到第二个人才能合，实际执行率低，代价是改动堆在本地迟迟不提交、`main` 反而更滞后。
- **选项**：A 维持原样（合规但推不动）｜B 取消强制签字，改由 A 统一审核合并｜C 取消 PR、直接 push `main`
- **决定**：**B**。PR 照旧提（保留 diff、验证方法与留痕），**审核人统一为 A（张鹏）**，不再强制第二人签字。
- **理由**：四人规模下「互相审核」的协调成本高于收益；A 兼进度把控与交付文档主笔，是天然的把关人。
- **兜底**：A 自己的 PR 无人可审 —— 改为「先跑一遍独立 AI 预检（照 `XQ-008-独立审核提示词.md` 那种可证伪结构），再对照 `docs/README.md` §三 验收标准自查后合并」。
- **不受影响**（这两条性质不同，**保留**）：
  - `docs/README.md` §三 里程碑验收「验收人 = 另一名成员，不可是该里程碑主要实现者本人」—— 这是「跑给验收人看」的交付要求，不是 PR 审核。
  - `需求规格说明书.md` 卷首「每份交付物必须有评审人」—— 针对交付文档（SRS / 报告 / PPT），不是代码 PR。
- **可逆性**：可逆。若出现「A 漏审导致 `main` 出问题」，恢复第二人签字即可。
- **参与人**：A（张鹏）提出并决定。
