# 决策记录（ADR）

> **写完就不再反复讨论**，除非有新证据。改技术选型必须追加新条目，不许改旧条目。
> 为什么留在 GitHub：① AI 接手任务时要读，避免把已定的事再议一遍；② 答辩要讲「当时为什么这么定」，需要版本留痕。
> 进度 / 分工 → **腾讯文档**（人读的不放这里）。

**模板**：

```markdown
### D-00x 决策标题（YYYY-MM-DD）
- **背景**：为什么要做这个决定
- **选项**：A / B / C 各自代价
- **决定**：选了哪个
- **理由**：一句话
- **影响**：谁要跟着改什么
- **可逆性**：可逆 / 不可逆（不可逆的必须四人一致同意）
- **参与人**：谁在场
```

## D-009 手机端路线改为自研原生 Android App（2026-10-13）

- **背景**：D-002 定的是「协议优先、客户端零开发」，手机侧用系统现成工具（iOS 快捷指令 / Android HTTP Shortcuts）零代码接入。本条推翻 D-002 的路线选择，改为自研原生 Android App。
- **为什么放弃 iOS**（三条硬事实，非偏好）：
  1. **iOS 拿不到「应用时长」**：必须走 Screen Time API，需 `com.apple.developer.family-controls` entitlement。Apple 官方明确非家长监护用途通常被拒；Distribution 签名的 entitlement 属 managed capability，需提交申请，**审核 4–8 周且不保证通过**，TestFlight 亦不可用。
  2. **无macOS 开发环境**：本项目开发环境为 Windows + WSL，Xcode 为 macOS 独占，无法构建 iOS 端。
  3. HealthKit 读步数本身可行（免费开发者账号 + 开发签名即可），但**只能拿到步数**，拿不到应用时长 —— 而应用时长是本次改动的目标之一。
- **选项**：A 双端原生 App（iOS + Android）｜B维持 D-002 零开发接入｜**C 只做 Android 原生 App，放弃 iOS**
- **决定**：**C**。自研 **Android 原生 App**（Kotlin + Health Connect），不再支持 iOS。
- **理由**：Android 侧无 Apple entitlement 审批门槛，且 Health Connect + UsageStatsManager 能同时提供步数与手机应用时长，正好补上 iOS 拿不到的那一半；单端也能把工期压到可承受范围。
- **影响**：
  - W11 产出物从「快捷指令模板」改为「Android App 工程 + 上报逻辑 + 真机验证记录」，主责仍为 **D**。
  - **接口零改动即可承载**：`POST /api/ingest/health` 的 `steps` 字段直接复用，仅`source` 枚举需新增 `android-app`。
  - `phone` 快照需**新增** `screen_minutes` / `top_apps` 字段（只增不改，符合 Git 纪律第3 条）。
  - 新增 Android 工具链前置条件：JDK 17（本机已装 Android SDK，但**未装 JDK**）。
  - **W10 与 W11 的语义不可合并**：电脑侧是「实时前台应用 + session_sec」，手机侧是「区间累计分钟」，详见接口协议 §3.6。
- **风险**：
  - 需至少 1 台 **Android 真机**（模拟器无计步传感器，Health Connect 取不到真实数据）。
  - Android 13 及以下需用户另装 Health Connect APK；14+ 系统内置。
  - 后台读取需 `READ_HEALTH_DATA_IN_BACKGROUND` + WorkManager 周期任务（官方示例 1 小时一次），先探测 `FEATURE_READ_HEALTH_DATA_IN_BACKGROUND`，不可用则降级为前台读。
  - 「手机应用时长」用 `UsageStatsManager` + `PACKAGE_USAGE_STATS`（系统级特殊权限，须引导用户手动开启）；最小有效窗口 60 秒，Android R+ 锁屏返回 `null` → **拿不到实时的「当前前台 App」**，只能拿区间累计值。
  - **语言栈风险**：D 现有技能为 Python + pywin32，Kotlin 为新增栈，需评估学习成本（待确认）。
- **可逆性**：可逆（接口层只增字段；App 侧若卡壳可退回 D-002 的零开发接入，接口不动）。
- **参与人**：张鹏（A）决定，待B、C、D 追认。

## D-010 姿态估计采用 MediaPipe 1.x Tasks API（2026-09-23）

> **状态：已废止（2026-11-17）**——实时链已整条删除，抽检（Lightweight OpenPose）为唯一姿态源，见 **D-016**。以下为历史记录，勿按本文实施。

> 编号说明：本决策形成于 2026-09-23 团队会议；合入时（2026-10-23）发现编号与 D-009（手机端路线，2026-10-13）撞号，改为 **D-010**。决策内容未变，仅改编号。

- **背景**：`requirements.txt` 原先写 `mediapipe>=0.10.14`，实际安装取到 **1.0.1**；而 MediaPipe 1.0 **移除了旧的 `mp.solutions.*`（Solutions API）**，`vision/pose_estimator.py` 里的 `mp.solutions.pose` 直接抛 `AttributeError`，被外层 `except Exception` 吞掉后**静默降级**为"永远无人"——真机姿态链失效且不报错（M1-1/1-2/1-3 全废，现场极难查）。
- **选项**：A 钉回 `mediapipe<1.0`（旧 API，代码零改动，但 0.10.x 无 Python 3.13 轮子且不再更新）｜B 迁移到 1.x **Tasks API**（`PoseLandmarker`，需 `.task` 模型文件）｜C 换用其它姿态方案
- **决定**：**B**。依据 2026-09-23 团队会议「暂时使用最新版 mediapipe」。
- **理由**：新版能力完整（`PoseLandmarker` 输出同样的 33 点归一化坐标 + `visibility`，索引与 BlazePose 一致），是上游主推方向；迁移面仅 **1 个文件**（`infer()` 契约不变，`compute_metrics` / 规则 / 状态机 / Hub 零改动）；避免被 0.10.x 版本冻结绑死。
- **影响**：
  - `requirements.txt`：`mediapipe>=0.10.14` → **`mediapipe>=1.0`**；
  - 新增模型资产 `backend/models/pose_landmarker_lite.task`（约 5.5 MB，**提交进仓库**，保证 M4-5「干净机器从零跑」不依赖临时下载）；
  - `config.yaml` 新增 `vision:` 节（模型路径 / `num_poses` / 检测与跟踪置信度可配 → 服务 M2-2「改配置不改代码」）；`config.py` 增加 4 个对应字段；
  - `pose_estimator.py` 整体重写；**不再静默降级**：依赖缺失 / 模型缺失 / 路径错误一律 `ok=False` + 可读 `last_error`，并由采集线程推 `error` 帧；
  - `camera.py`：`_BaseThread._handle` 改名为 **`_on_observation`** —— Python 3.13 的 `threading.Thread.__init__` 会设置实例属性 `self._handle`（`_thread._ThreadHandle`），**遮蔽同名方法**，导致采集线程启动即崩（`TypeError: '_thread._ThreadHandle' object is not callable`）；
  - **模型必须以字节缓冲加载**：`BaseOptions(model_asset_buffer=...)`。mediapipe 的 C++ 层对**非 ASCII 路径**（本项目位于 `G:\中级实训\`）会报 `Unable to open file`，改用 buffer 可绕过；
  - **P4「是否引入 Git LFS」可以关闭：不需要** —— 5.5 MB 远低于 GitHub 单文件上限。
- **可逆性**：可逆。换回 0.10.x 只需把加载方式改回路径式 API；`infer()` 契约未变，上层不受影响。
- **验证**（本机 Python 3.13.7 / CPU / 无独显）：
  - `PoseEstimator.ok = True`，模型加载成功（`Created TensorFlow Lite XNNPACK delegate for CPU`）；
  - 空帧 → `person_present=False`；连续 60 帧无异常；单帧推理 ≈ **31.7 ms**（lite 模型，10 Hz 采样绰绰有余）；
  - `--sim` 起服后 WS 正常推送 `state`：`upright` → `away` → `slouch`（`neck_angle_deg=34.7`）；
  - 20 个 Python 文件语法检查 0 失败。
- **参与人**：四人（团队会议定方向，C 落地实现）。

## D-012 审核流程精简：取消强制第二人签字（2026-09-28）

- **背景**：原 `docs/README.md` §二 第 1 条要求每个 PR「至少 1 人 approval，写码人不能自评」。四人小组下每条改动都要凑到第二个人才能合，实际执行率低，代价是改动堆在本地迟迟不提交、`main` 反而更滞后。
- **选项**：A 维持原样（合规但推不动）｜B 取消强制签字，改由 A 统一审核合并｜C 取消 PR、直接 push `main`
- **决定**：**B**。PR 照旧提（保留 diff、验证方法与留痕），**审核人统一为 A（张鹏）**，不再强制第二人签字。
- **理由**：四人规模下「互相审核」的协调成本高于收益；A 兼进度把控与交付文档主笔，是天然的把关人。
- **兜底**：A 自己的 PR 无人可审 —— 改为「先跑一遍独立 AI 预检（照 `XQ-008-独立审核提示词.md` 那种可证伪结构），再对照 `docs/README.md` §三 验收标准自查后合并」。
- **不受影响**（这两条性质不同，**保留**）：
  - `docs/README.md` §三 里程碑验收「验收人 = 另一名成员，不可是该里程碑主要实现者本人」—— 这是「跑给验收人看」的交付要求，不是 PR 审核。

- **可逆性**：可逆。若出现「A 漏审导致 `main` 出问题」，恢复第二人签字即可。
- **参与人**：A（张鹏）提出并决定。

## D-013 健康伙伴改为程序化自建（2026-10-27）

- **背景**：P3「美术素材来源」一直挂着。试用的两个下载件（`model.glb` 50,004 面 / `blue+monster.usdz` 454,314 面）**都是单网格静态件**：无骨骼、无 animation clip、无可拆部件节点。而 M3-2 要「≥4 个姿态状态有不同表现」、M3-3 要「切换有过渡补间」，单网格只能整物体倾斜，「伏案 / 喝水」这类需要手臂与头部分离的状态做不出来。
- **选项**：A 拿 GLB 当占位壳子，只做整体姿态｜B 另找带骨骼 + 动画片段的 CC0 low-poly｜C 按 `room.js` 同一套口径程序化自建
- **决定**：**C**。`frontend/src/scene/partner.js` 生成蓝粘土小怪（照 `怪物形象三视图绘制.png/.jpeg` 量比例），躯干 / 头 / 双臂 / 双腿 / 尾巴各自是独立 Group，六状态只改旋转与位移，过渡由 `update(dt)` 指数插值。
- **理由**：
  - 与房间同源 —— 共用 `materials.js` 的 `clay()`（roughness 0.9 / metalness 0），零外部贴图、零新增依赖，风格不会「两个世界」；
  - 面数可控 —— 13,354 面对比下载件的 50,004 / 454,314；
  - 许可干净 —— 下载件都没有 license 字段，XQ-010 要求登记来源与许可；
  - 体积 —— `model.glb` 26.62 MB 已超过前端「单文件 >20 MB 不进仓库」的约定。
- **代价 / 兜底**：造型上限不如手工雕刻；且姿态是「整段肢体旋转」，做不出指节级细节。若 M3-7「展示效果达标」判定不过，可在**不改调用方**的前提下换成带骨骼的 glb —— `partner.js` 对外只暴露 `group / setState / update / getState`，替换范围限于这一个文件。
- **可逆性**：可逆。
- **参与人**：A（张鹏）。

## D-014 坐姿检测改为「定期抽检」+ 换 Lightweight OpenPose（2026-11-16）

- **背景**（两条独立但同向的问题）：
  1. **算力**：任课老师提醒，实时姿态监测会持续占用大量计算机资源；团队决定改为**定期拍摄抽检**，不再常驻实时推理。
  2. **精度**：D-010 选的 MediaPipe BlazePose 在本项目的真实场景（伏案、侧向、上半身、宽松外套、大耳机）下**关键点位置不可用**。2026-11-11 用同一批照片实测：肩线角算出 63.9° / 93.9° / 132.2°（正常应 <15°），而 visibility 仍报 1.00 —— 即"错得很自信"，比漏检更危险。根因是 **top-down 架构**：先框人再在框内回归 33 点，看不见的点也会靠先验"猜"一个坐标。
- **选项**：
  - A 继续用 MediaPipe，自建几百张图手工标注耳/肩做微调 —— 标注 33 点约 2–5 分钟/张，300 张需 10–25 小时，且 MediaPipe 是闭源 TFLite、**没有官方微调接口**，等于自训一个关键点回归网络
  - B 换 **YOLOv8-pose**（top-down，仍是同类架构，且 AGPL-3.0 传染性强、依赖含 torch 200MB+）
  - C 换 **OpenPose**（bottom-up，但原版要 Caffe+CUDA，CPU 上 1–2 FPS、2020 年后停更、仅限非商业）
  - D 换 **Lightweight OpenPose**（OpenPose 的 bottom-up 架构 + MobileNetV1 骨干，CPU 可跑，ONNX/OpenVINO 可导出）
- **决定**：**D**。同时把检测模式从「实时」改为「**定期抽检**」（默认 60 秒一次）。
- **理由**：
  - bottom-up 先出关键点、再用 PAF 连成人，**连不上就不连** —— 实测四张样图，关键点位置肉眼核对全部贴位；头出画时只标出可见的颈/肩/肘/腕，不硬凑骨架（`01.png` 只连出 6 点，而 MediaPipe 在该图上直接判无人体）；
  - 18 点里**自带 `neck`（索引 1）**，正是算头前倾最需要的锚点，COCO 17 点与 BlazePose 都没有（旧实现拿双肩中点硬代替）；
  - 抽检把"帧率"这个约束整个卸掉了，可以选精度优先的方案。
- **影响**：
  - 新增 `vision/pose_lw.py`（推理封装）、`rules/sitting_rules.py`（指标与判定）、`vision/spot_check.py`（抽检线程）；
  - 新增接口 `GET /api/sitting/latest`、`GET /api/sitting/history`、`POST /api/sitting/check`（协议未定义，属「只增不改」的增）；
  - `config.yaml` 新增 `sitting:` 节（周期、模型路径、阈值、线程数）；
  - **依赖与资产不进库**：`torch`（CPU 版约 200MB）+ LW 仓库 + 88MB 权重 `checkpoint_iter_370000.pth`，均在 `backend/models/README.md` 给出一次性准备步骤；`.gitignore` 已加防护（`backend/models/*.pth`、`*.onnx`、`lightweight-human-pose-estimation.pytorch/`）；
  - **验收口径需同步**：抽检模式下 M1-5「3 秒内跟随」、NFR-P-01「端到端 ≤1.5s」、M3-6「30 分钟帧率」不再适用，需改为「抽检周期内更新 / 单次分析耗时 / 连续抽检稳定性」。**此项已由 D-016 定案：AC-02 / NFR-P-01 口径作废。**
- **性能记录**（2026-11-17 复测，Ryzen 5 6600H 12 线程 / Python 3.14 / torch 2.15.0+cpu / 640×480 实拍帧，每格 5 次取中位数）：
  | height_size | 1 线程 | 2 线程 | 4 线程 |
  |---|---|---|---|
  | 256 | 114 ms | 67 ms | 42 ms |
  | 320 | 179 ms | 103 ms | 65 ms |
  | 384 | 273 ms | 154 ms | 97 ms |

  首次调用（含算子初始化）只比稳态高 3–10 ms，无冷启动尖峰；`detect_image.py` 端到端 113 ms。**多线程变快而不是变慢**，「depthwise conv 多线程拖慢」在本机无法复现。
- **原记录（已被上面的复测取代，保留备查）**：16 核 / Python 3.13 / torch 2.15.0+cpu，12 线程 17 s、4 线程 34 s、单线程 6 s，叠加浏览器争抢可达 68 s —— 与本机实测差 30–50 倍，疑为当时混入首次加载或宿主极端争抢，**不要再用 3–6 s 这个数字对外引用**。`sitting.torch_threads` 仍保持 1（组员机器核数未知，单线程最稳），但本机可以调到 4。
- **对 D-016 的影响**：既然单帧 0.1 s，抽检不再受算力限制，60 s 周期是产品选择而不是性能约束；「抽检因为实时带不动」这个理由不成立，D-016 的删除理由以「少一套依赖 / 少一份口径 / 少一条与抽检抢设备的链路」为主，与算力无关（D-016 正文未以性能为由）。
- **可逆性**：可逆，但需重新引入整套 MediaPipe 依赖、模型与实时采集线程（见 **D-016**）。旧的 MediaPipe 实时链路已由 **D-016** **整条删除**（`pose_estimator.py`、`camera.py` 的 `CaptureThread`、`pose_landmarker_lite.task`）；抽检是**唯一**姿态源，不存在「互斥 / 回退」两选一：`sitting.enabled: false` 或模型未就绪时后端**没有任何姿态数据**（`/api/health` 的 `sitting.model_ready=false` + `last_error`），只有 `--sim` 还能造模拟状态。
- **口径变更声明**（2026-11-17 审核补充，单人可复核）：
  1. `state_machine.debounce` 的键名原来带 `_sec` 后缀，与 `debounce_for(state)` 的短键永远对不上，**所有状态实际都在用 `default_sec=2.0`**。修掉后缀后 `1.0 / 4.0 / 1.5` 三档才真正生效 —— 这是**行为变化**：away 从 2s 变 4s、upright 变 1.5s、unknown 变 1s，历史统计里的状态持续时长与新数据不完全可比。
  2. `posture_rules.compute_metrics` 新增 `head_pitch_deg` / `view`，`shoulder_tilt_deg` 在侧向视角下为 `None`（原来恒有值）。前端不读这些字段，但报告脚本若按旧 schema 取值需允许 `null`。
  3. 抽检结果不再冒充 `type:"state"` 推送，改为独立的 `type:"sitting"`（`hello` 快照里为 `sitting` 键）。它**不经过**状态机的防抖/滞回，属于另一条判定通路，不得与实时状态合并统计。
  4. 抽检单帧未检出人记 `unknown/no_person`，**连续两轮**未检出人才记 `away/no_person_away`，避免构图失败被计成"离开时长"。
  5. `sitting.enabled` 代码默认值改为 `false`（实时链已删，见 D-016；开发机在 `config.yaml` 里显式开启）。
- **未定项**：判定阈值目前是**绝对角度**（`head_pitch ≥ 58°` → slouch / `torso_lean ≥ 20°` → desk_hunch），尚未做个人化校准（M2-1）。注意 `sitting_rules.head_pitch_deg`（颈→耳与竖直夹角）与 `posture_rules.head_pitch_deg`（耳→肩与竖直夹角）**同名不同定义**，两者不可横向比较；且实时链已删（D-016），M2-1 的校准链路（`calibration.py` 基线）只服务 `--sim`，对抽检结果不生效。
- **参与人**：团队（症状与样图由老师指导、组长联调暴露）；C 落地实现与实测。

## D-015 · 平台策略：一套实现，Windows / Linux 两端可跑（开发机为 Linux）

- **状态**：已定（2026-11-17）
- **背景**：组长开发机在 2026-11 由 Windows 换成 Ubuntu（GNOME / **Wayland**），组员机器仍是 Windows。若按「只支持 Linux」收口，组员无法运行与联调；若按「两套实现」铺开，摄像头后端、错误提示、采集能力会各自漂移，数字也不可比。
- **决定**：
  1. **代码只有一份**，两端都能跑；平台差异**只收敛到一个文件** `backend/xiaoqi/vision/camera_util.py`（按 `sys.platform` 选后端与提示文案），别处一律调 `open_capture()`，禁止就地写 `CAP_*` 或平台分支。
  2. **开发与验收基线 = 本机 Linux**：命令、`.venv`、性能数字以本机为准；Windows 端以「组员机器能起服务、能开摄像头」为验收下限。
  3. 两端的平台事实各自记录，不互相套用（Wayland 拿不到全局焦点；DSHOW/MSMF 只在 Windows 存在）。
- **落地**：
  1. 新增 `camera_util.py`：Windows 依次 DSHOW → MSMF → ANY，Linux 依次 V4L2 → ANY；失败给平台对应的三条排查动作。`camera.py`（`--sim` 模拟线程）、`spot_check.py`（抽检）、`scripts/framing_check.py` 全部改为调用它。
  2. `requirements.txt` 恢复 `pywin32>=306 ; sys_platform == "win32"` 与 `psutil`，与 Linux 侧 X11 方案并列写明。
  3. `AGENTS.md`：写明「一套实现、两套平台」，并给出 Linux / Windows 两套启动命令。
  4. `README.md` / `review.md` / `需求规格说明书.md`（C-01、NFR-C-01）/ `系统架构.md` / `UML建模.md` / `frontend/README.md`：平台行、验收判据改为双端表述，性能数字标注取自哪台机器。
- **影响**：
  - W10 行为采集在 Linux 本机 **Wayland 下不可行**（拿不到全局前台窗口），X11 的 `XGetInputFocus` / `xdotool` 在此不可用 → 方案待定，见 P10；Windows 侧 pywin32 方案不变。
  - Android SDK 原在 Windows 机 `D:\Android\Sdk`，本机未装（JDK 亦未装），需重装。
- **可逆性**：可逆（去掉 `camera_util` 的平台分支即回到单平台，但两端会再次漂移，不建议）。
- **参与人**：组长（C）落地；Windows 端事实由组员机器验证。

## D-016 · 删除 MediaPipe 实时链，抽检为唯一姿态源（2026-11-17）

- **状态**：已定（2026-11-17）
- **背景**：D-014 之后系统里同时存在两条姿态链路——实时链（MediaPipe PoseLandmarker，常驻推理）与抽检链（Lightweight OpenPose，60s 一次）。两者要打开同一个摄像头 index，只能二选一（同时开会得到「抽检永远打不开」或「实时链每 3 秒 POSE_LOST」）；实时链还常驻占用算力，而 D-014 已实测其关键点在伏案 / 侧向场景下不可用。留一条用不上、又要与抽检抢设备的链路，只会让启动分支与文档口径继续漂移。
- **选项**：A 两条都留、运行时二选一｜B 删除实时链，抽检为唯一姿态源｜C 删除抽检，保留实时链
- **决定**：**B**。整条删除实时链：`backend/xiaoqi/vision/pose_estimator.py`、`backend/xiaoqi/vision/camera.py` 的 `CaptureThread`、`backend/models/pose_landmarker_lite.task`；`requirements.txt` 去掉 `mediapipe`，**`torch` / `torchvision` 变为必需依赖**。`config.yaml` 的 `vision:` 整段与 `camera.fps` 一并删除，`config.py` 同步移除 `camera_fps`（抽检帧率由 `sitting.interval_sec` 决定，不再有常驻取流）。抽检（`spot_check.py` + `pose_lw.py`）成为**唯一**姿态源；`--sim`（`SimThread`）保留，供无摄像头时开发前端。
- **理由**：单一姿态源 = 单一启动分支、单一口径、单一文档。实时链的能力已被 D-014 实测否定，它唯一的「价值」是回退，而回退到坏数据比没有数据更危险——前端与报告会把错判当成真姿态。
- **影响**：
  - 没有 torch / LW 权重时后端**不降级**：`GET /api/health` 的 `sitting.model_ready=false`、`last_error` 写明缺哪一步，且**没有任何姿态数据**（无 `state` 推送；`/api/sitting/latest` 返回未启用 / 未就绪）；启动时向 WS 客户端广播 `{"type":"error","code":"POSE_UNAVAILABLE","message":"<原因>"}`。
  - `/api/health` 的字段由 `realtime` 改为 **`pose_source`**：`"sim"`（`--sim` 合成）/ `"spot_check"`（真机抽检就绪）/ `null`（无姿态源）。前端与报告只认这一个来源字段。
  - `需求规格说明书` 中 **AC-02、NFR-P-01 的实时口径作废**（已无实时链可测），验收改为「抽检周期内更新 / 单次分析耗时 / 连续抽检稳定性」。
  - `--sim` 仍可开发前端（模拟 `type:"state"`），但不代表真机姿态可用。
  - 平台策略不变：`camera_util.py` 仍是唯一的平台差异点（抽检与 `--sim` 共用）。
  - 文档同步：`README.md`、`系统架构.md`、`review.md`、`backend/models/README.md`、PR 模板里的实时 / MediaPipe 表述一并改为 LW 抽检。
- **可逆性**：可逆，但需重新引入整套 `mediapipe` 依赖、`.task` 模型与实时采集线程（`pose_estimator.py` / `CaptureThread`），即重做 D-010。
- **参与人**：团队（D-014 之后收敛）；C 落地删除。
