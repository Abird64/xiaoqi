# 决策记录（ADR）

> **写完就不再反复讨论**，除非有新证据。改技术选型必须追加新条目，不许改旧条目。
> 为什么留在 GitHub：① AI 接手任务时要读，避免把已定的事再议一遍；② 答辩要讲「当时为什么这么定」，需要版本留痕。
> 进度 / 分工 → **腾讯文档**（人读的不放这里）。

**模板**：

```markdown
### D-00x 决策标题（YYYY-MM-DD）
- **背景**：为什么要做这个决定
- **选项**：A / B / C 各自代价
- **决定**：选了哪个
- **理由**：一句话
- **影响**：谁要跟着改什么
- **可逆性**：可逆 / 不可逆（不可逆的必须四人一致同意）
- **参与人**：谁在场
```

## D-001 前端采用 Three.js 3D 路线，2.5D 作为降级预案（2026-09-06）

- **背景**：房间世界是多媒体课的核心卖点，但 3D 美术与性能都有风险。
- **选项**：A 纯 2.5D 等距精灵（稳但作品感弱）｜B Three.js 3D（上限高、风险高）｜C 先 2.5D 再升级
- **决定**：**B**，并保留 A 作为降级预案。
- **理由**：作品感是这门课的核心评分点；降级预案保证最坏情况仍可交付。
- **影响**：前端工作量集中在 B 身上；W10 设降级触发器。
- **可逆性**：可逆（状态驱动内核不变，换渲染层不影响后端）。
- **参与人**：三人 + 教师方向确认。

## D-002 手机端数据「协议优先，客户端零开发」（2026-09-14）

- **背景**：老师建议加入手机数据（步数/静止），但自研 App 工期不够。
- **选项**：A 自研 App 对接 HealthKit / Health Connect｜B 系统现成工具（快捷指令 / HTTP Shortcuts）+ 后端暴露带令牌接口｜C 不做手机端
- **决定**：**B**。电脑端提供 `POST /api/ingest/health`，手机侧零代码接入。
- **理由**：手机只作为一路**数据源**，不是客户端；省掉开发、审核、上架。
- **影响**：后端承担令牌校验与幂等去重；前端只消费聚合后的步数。
- **可逆性**：可逆（接口不变，换数据来源而已）。
- **参与人**：三人。

## D-009 房间坐标与尺寸口径（2026-09-28）

- **背景**：XQ-008 搭 3D 房间时定了「1 单位 = 1 米、房间 6×6 m、后墙 z=-3、左墙 x=-3」这套口径，但只写在 `frontend/README.md` 与 `room.js` 头注释里，`docs/` 此前无任何空间坐标定义。B（家具）与 C（状态→场景映射）不一定会读前端 README，各按各的尺子写就会对不上。
- **选项**：A 各人自定（返工风险高）｜B 只留在 `frontend/README.md`（同上）｜C 进决策记录成文
- **决定**：**C**。房间空间口径如下，**任何人在房间里加东西都按这个来**：

  | 项 | 取值 |
  |---|---|
  | 单位 | **1 单位 = 1 米** |
  | 轴向 | y 轴朝上（Three.js 默认）；地面 `y = 0` |
  | 房间尺寸 | 6 m × 6 m；墙高 3 m |
  | 后墙 | `z = -3`（法线朝 +z） |
  | 左墙 | `x = -3`（法线朝 +x） |
  | 敞开的另两面 | `+z`、`+x` 不砌墙，给相机留机位 |

- **理由**：跨成员共用的空间口径必须有唯一真源，否则 M3 摆家具与做状态映射时会互相打架；决策记录是「AI 接手任务时要读」的文件，放这里命中率最高。
- **影响**：B（M3-1 家具）与 C（状态→场景映射）须按此口径；`frontend/README.md` 保留同一份口径作实现侧说明，**若两者冲突以本条为准**。
- **可逆性**：可逆，但已摆放的物体坐标要跟着改。
- **参与人**：A（张鹏）提出，待 B、C 追认。

## D-010 审核流程精简：取消强制第二人签字（2026-09-28）

- **背景**：原 `docs/README.md` §二 第 1 条要求每个 PR「至少 1 人 approval，写码人不能自评」。四人小组下每条改动都要凑到第二个人才能合，实际执行率低，代价是改动堆在本地迟迟不提交、`main` 反而更滞后。
- **选项**：A 维持原样（合规但推不动）｜B 取消强制签字，改由 A 统一审核合并｜C 取消 PR、直接 push `main`
- **决定**：**B**。PR 照旧提（保留 diff、验证方法与留痕），**审核人统一为 A（张鹏）**，不再强制第二人签字。
- **理由**：四人规模下「互相审核」的协调成本高于收益；A 兼进度把控与交付文档主笔，是天然的把关人。
- **兜底**：A 自己的 PR 无人可审 —— 改为「先跑一遍独立 AI 预检（照 `XQ-008-独立审核提示词.md` 那种可证伪结构），再对照 `docs/README.md` §三 验收标准自查后合并」。
- **不受影响**（这两条性质不同，**保留**）：
  - `docs/README.md` §三 里程碑验收「验收人 = 另一名成员，不可是该里程碑主要实现者本人」—— 这是「跑给验收人看」的交付要求，不是 PR 审核。
  - `需求规格说明书.md` 卷首「每份交付物必须有评审人」—— 针对交付文档（SRS / 报告 / PPT），不是代码 PR。
- **可逆性**：可逆。若出现「A 漏审导致 `main` 出问题」，恢复第二人签字即可。
- **参与人**：A（张鹏）提出并决定。
