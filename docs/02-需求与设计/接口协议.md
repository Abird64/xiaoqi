## 一、角色与方向

| 角色 | 是谁 | 做什么 |
|---|---|---|
| 后端（服务方） | 成员 C | 姿态/行为/手机数据汇总 → 通过 WebSocket 推给前端；对外提供 HTTP 接入 |
| 前端（消费方） | 成员 A | 消费 WebSocket 消息，渲染房间与伙伴；**只读，不反向控制**（v0.1 不做） |
| 数据源（外部） | 成员 D | 手机（快捷指令 / HTTP Shortcuts）通过 HTTP 上报；Windows 行为采集在本地进程内 |

```
手机 ──HTTP POST /api/ingest/health──┐
摄像头+Windows ──本地进程──▶ 后端 C ──WebSocket /ws──▶ 前端 A
```

【修订】前端「不反向控制」的表述保留，但 §3.5 开了一条**只用于校准、不含任何业务控制**的反向通道。

## 二、通用约定

| 项 | 约定 |
|---|---|
| 协议版本 | 每条消息带 `v`（整数）。v0 系列内**只增字段**，前端必须忽略未知字段 |
| 时间戳 | 一律为 **Unix 毫秒**（`1789526000123`），未知时用 `null`，不要用 0 |
| 命名 | **snake_case**（`neck_angle_deg`） |
| 状态值 | 全小写英文枚举，见下 |
| 推送频率 | 后端推送 ≤ **1 条/秒**（状态变化时才推；心跳另计） |
| 数值单位 | 角度 `deg`、时长 `sec`、距离 `cm`、步数 `步` |

### 姿态状态枚举 `pose_state`（**已确认，改动必须四人同意**）

| 值 | 中文 | 含义 |
|---|---|---|
| `unknown` | 未知 | 未检测到人 / 置信度过低 |
| `upright` | 坐直 | 正常良好坐姿 |
| `slouch` | 驼背 | 头前倾 + 躯干后靠 |
| `desk_hunch` | 伏案 | 躯干前倾逼近桌面 |
| `away` | 离开 | 座位上没有人 |
| `drinking` | 喝水 | 抬臂举杯（**v0.1 可选**，识别不稳就先不做） |

【修订】**`drinking` 保留枚举值**（已定稿）。A 的 M3 表现层先只做 5 个状态，`drinking` 的动画留到以后再加 —— 写进协议零成本，砍掉反而以后要动已冻结文档。

### 行为等级枚举 `behavior_level`

| 值 | 含义 |
|---|---|
| `ok` | 正常 |
| `warn` | 持续偏长，房间环境给出轻提示 |
| `alert` | 超过阈值，触发角色提醒 |

## 三、WebSocket `/ws`

连接：`ws://<后端地址>:8000/ws`（无鉴权，v0.1 仅局域网使用）

### 3.1 `hello`（连接建立后**第一帧**，全量快照）

```json
{
  "v": 1,
  "type": "hello",
  "ts": 1789526000123,
  "server": { "version": "0.1.0", "capabilities": ["pose", "behavior", "phone"] },
  "pose": { "state": "upright", "confidence": 0.91, "since_ts": 1789525990000 },
  "behavior": { "active_app": "Code.exe", "session_sec": 1830, "level": "ok" },
  "phone": { "steps": 3210, "updated_ts": 1789525000000, "stale": false }
}
```

### 3.2 `state`（增量推送，只带**发生变化**的顶层字段）

```json
{
  "v": 1,
  "type": "state",
  "ts": 1789526010000,
  "pose": {
    "state": "slouch",
    "confidence": 0.87,
    "since_ts": 1789526008000,
    "sustained_sec": 2.0,
    "metrics": { "neck_angle_deg": 42.3, "shoulder_tilt_deg": 3.1, "distance_cm": 62 }
  }
}
```

- `metrics` 仅用于调试与可视化，**前端不得依赖它做逻辑判断**（字段可能缺失）。
- `sustained_sec` = 当前状态已持续时长，前端做过渡动画的时间基准。

### 3.3 `reminder`（提醒事件）

```json
{ "v": 1, "type": "reminder", "ts": 1789529600000, "kind": "water", "level": "alert" }
```

`kind` 取值：`water`（喝水）｜`standup`（久坐起身）｜`focus`（久用屏幕，【修订】对应 `behavior_level.alert`）。

### 3.4 `ping` / `error`

```json
{ "v": 1, "type": "ping", "ts": 1789526010000 }
{ "v": 1, "type": "error", "ts": 1789526010000, "code": "POSE_LOST", "message": "摄像头断流" }
```

前端收到 `ping` 忽略即可；连续 **10 秒**无任何消息视为断线，自动重连（间隔 2s 递增，最长 30s）。

### 3.5 `client`（前端 → 后端，【修订】新增）

> **为什么要这条**：M2-1 的验收标准是「有个人化校准流程（**启动时按提示「坐直」采样基准**）」。
> 引导界面在 A 手上，采样本体在 C 的摄像头进程里 —— 前端必须能告诉后端「我要开始采了 / 采完了」。
> 本通道 v0.1 **只用于校准**，不含任何业务控制，不违反「前端只读」的定位。

```json
{ "v": 1, "type": "client", "ts": 1789526010000, "action": "calibrate_begin" }
{ "v": 1, "type": "client", "ts": 1789526030000, "action": "calibrate_commit" }
```

| `action` | 后端行为 |
|---|---|
| `calibrate_begin` | 清空基准，开始按当前坐姿采样 |
| `calibrate_commit` | 锁定采样结果作为 `upright` 基准，并推送一帧 `state` |
| `calibrate_cancel`（可选） | 放弃本次采样，保留旧基准 |

**【已定稿】本通道保留。** 依据：M2-1 验收标准原文是「启动时**按提示**「坐直」采样基准」——有"提示"就说明界面在 A 手上，因此必须由前端发起校准。

## 四、HTTP 接入 `POST /api/ingest/health`

**用途**：手机侧零开发上报（iOS 快捷指令 / Android HTTP Shortcuts）。

| 项 | 约定 |
|---|---|
| 路径 | `/api/ingest/health` |
| 鉴权 | Header `X-Xiaoqi-Token: <配对令牌>`（后端首次启动生成，打印在控制台并显示二维码） |
| 监听 | `0.0.0.0:8000`（手机与电脑需在同一 Wi-Fi） |
| 内容类型 | `application/json` |

### 请求体

```json
{ "steps": 3210, "ts": 1789526000000, "source": "ios-shortcut", "device_id": "iphone-zhang" }
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `steps` | ✅ | 当日累计步数（整数，聚合标量） |
| `ts` | ➖ | 采集时间；缺省时用服务端接收时间 |
| `source` | ➖ | `ios-shortcut` / `android-http-shortcuts` / `manual` |
| `device_id` | ➖ | 用于幂等去重的设备标识，缺省时按 IP 处理 |

### 响应

| 码 | 场景 | 体 |
|---|---|---|
| 200 | 接收成功 | `{ "ok": true, "deduped": false }` |
| 200 | 命中幂等（60 秒窗口内同 `device_id` 重复上报） | `{ "ok": true, "deduped": true }` |
| 400 | 字段缺失/类型错 | `{ "ok": false, "error": "INVALID_FIELD", "field": "steps" }` |
| 401 | 令牌错误 | `{ "ok": false, "error": "BAD_TOKEN" }` |

### 规则

1. **幂等**：同一 `device_id` 在 **60 秒**窗口内的重复上报直接丢弃（`deduped: true`），不覆盖已有值。
2. **只前进不回退**：`steps` 是当日累计值，若新值小于已存值（跨零点或系统重置），视为**新的一天**开新记录，不修正旧值。
3. **静止时长**由步数序列差分推断，**不额外申请权限**：连续 N 分钟步数无变化 → 计为静止。
4. iOS 定时自动化需要解锁才可靠触发 → 后端必须容忍**多次上报**与**长时间断流**；`phone.stale = true` 表示数据超过 15 分钟未更新。
5. 【修订】**`stale = true` 期间不累计静止时长。**
   原因：规则 3 靠「步数不变」判静止，规则 4 说「15 分钟没上报算 stale」。手机锁屏 20 分钟时两条会同时命中 → 用户明明在动（或根本没在用电脑），却被判「静止 20 分钟」→ 误触发 `standup`。
   正确语义：**没数据 ≠ 静止。** 只有在数据新鲜（`stale = false`）的前提下，步数序列不变才计入静止。

### 4.1 `GET /api/history`（【修订】新增 · 只读）

> **为什么要这条**：原文清单 #3 说「暂定 v0.2 再加」，#7 又问「是否 v0.1 一并冻结」，两条打架。
> 本版采纳 #7 的结论（现在加）——但**理由要改**：原文 #7 写「W8 再补要动已冻结文档」，这个理由不成立，按「只增不改」规则，新增接口属于"增"，合规。
> 真实成本是**联调返工的沟通成本**：M2 的误报/漏报报告 W7–W8 就要用，那时再定，D 的采集侧和 C 的存储侧都要改。

| 项 | 约定 |
|---|---|
| 路径 | `/api/history?from=<ms>&to=<ms>` |
| 方法 | `GET`，**只读** |
| 鉴权 | 同 `X-Xiaoqi-Token` |
| 分页 | v0.1 不分页，后端限制单次返回 ≤ 7 天，超出返回 400 |

```json
{
  "v": 1,
  "from": 1788912000000,
  "to": 1789516800000,
  "samples": [
    { "ts": 1789526000123, "pose_state": "upright", "neck_angle_deg": 12.4,
      "behavior_app": "Code.exe", "behavior_level": "ok", "steps": 3210 }
  ]
}
```

`samples` 按 `ts` 升序，缺测字段用 `null`。M2 的误报/漏报统计直接吃这个数组。

**【已定稿】本节保留**，`GET /api/history` 随 v0.1 一并冻结。
