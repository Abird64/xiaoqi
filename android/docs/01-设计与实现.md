# 设计与实现

> 目标：把「当日步数」可靠地送到小栖后端，且不改变参考项目的任何协议/代码。
> 本文说明为什么这样实现、边界在哪里、哪些地方以后可以替换。

---

## 1. 背景与约束

小栖的接口协议（`docs/02-需求与设计/接口协议.md`）已经把手机侧定义得很清楚：

- `POST /api/ingest/health`，Header `X-Xiaoqi-Token`；
- Body 必填 `steps`（当日累计、非负整数），可选 `ts` / `source` / `device_id`；
- `source` 在 D-009 增加 `android-app`；
- 后端对同 `device_id` **60 秒幂等**去重，步数**只前进不回退**；
- `phone.stale`：15 分钟未更新为 true；
- 前端 `steps.js`：没有数据时显示「无数据」而**不补 0**，stale 时显示「待同步」。

D-009 的原方案是 **Kotlin + Health Connect**，同时读手机应用时长。本项目只做“步数”
这一半，且需要在本机（Windows、无 Gradle、无网络、无真机）产出可安装 APK，所以做了
两个有意的取舍：

| 取舍 | 选择 | 原因 |
|---|---|---|
| 语言 | **Java**（Android Framework） | 本机无 Kotlin 编译器 / Gradle 缓存；Java 可直接用 `javac + d8` 离线构建 |
| 步数来源 | **`TYPE_STEP_COUNTER` + `TYPE_STEP_DETECTOR` 降级** | 不依赖 Health Connect APK/权限/联网依赖；Android 8+ 全兼容；实时、可解释 |
| UI | **纯 Framework 控件 + 自绘 RingView** | 不引入 AndroidX/Material 依赖，APK 约 190 KB，离线可编 |
| 网络 | **`HttpURLConnection`** | 只发一个 JSON，OkHttp/Retrofit 没必要；同一份纯 Java 代码可在 JVM 上联调 |

> **与 D-009 的关系**：本 App 是 D-009 的“步数链路”子集。协议完全兼容；应用时长
> （`screen_minutes` / `top_apps`）未实现。以后若换 Health Connect，只需替换
> `StepTracker` 的数据来源，`SyncClient` / 服务 / UI 不用动。

## 3. 当日步数算法

### 3.1 传感器语义

- `TYPE_STEP_COUNTER`：返回**开机以来**的累计步数（float，整数步），重启归零；
  需要 `ACTIVITY_RECOGNITION` 运行时权限（Android 10+）。
- `TYPE_STEP_DETECTOR`：每检测到一步发一个事件，没有累计值；作为没有 counter 的降级。

“今日”不能直接取 counter 值，必须维护增量。

### 3.2 持久化状态

SharedPreferences（`xiaoqi_steps_config`）：

| key | 含义 |
|---|---|
| `step_day` | 当前统计日 `yyyy-MM-dd`（设备本地时区） |
| `step_today` | 当日累计步数 |
| `step_last_total` | 上次 counter 读数（跨重启保留） |
| `step_last_ts` | 上次传感器事件时刻（Unix ms） |

### 3.3 伪代码

```text
onCounter(total, now, today):
    if 第一次运行（day 为空 或 lastTotal < 0）:
        day = today; lastTotal = total; lastTs = now
        return 0                      # 不把“开机以来”算进今天

    rolled = (day != today)
    if rolled: day = today; todaySteps = 0

    gap = now - lastTs
    if total >= lastTotal: delta = total - lastTotal
    else:                   delta = total          # 重启/传感器归零

    if rolled and gap > 2h: delta = 0              # 跨天断流，无法拆分归属
    if gap > 0 and delta > gap秒×5 + 2000: delta = 0   # 物理上限
    if gap <= 0 and delta > 2000: delta = 0

    todaySteps += delta
    lastTotal = total; lastTs = now
```

### 3.4 边界行为

| 场景 | 例子 | 结果 | 说明 |
|---|---|---|---|
| 首次安装 | 开机累计 5000，首次读数 5000 | 今日 0 | 不虚报安装前的步数；下一次走动开始累计 |
| 正常增量 | 5000 → 5100 | +100 | |
| 跨零点（服务在跑） | 23:59 读数 5200，00:05 读数 5250 | 新一天 +50 | 跨零点的几小步计入今天 |
| 跨天 + 长时间断流 | 昨天 20:00 读数 1000，今天 10:00 读数 5000 | 今日 0 | 14 小时的 4000 步无法拆分，宁可少算 |
| 重启 | 昨读数 8000，重启后读数 20 | +20 | 重启后的步数全部算今天 |
| 异常跳变 | 10 秒内 1000 → 100000 | 0 | 超过 5 步/秒的物理上限 |
| 降级计步器 | 每个 detector 事件 | +1 | 没有累计值，无法防跳变 |
| UI 零点刷新 | 没有新传感器事件，00:00 打开 App | 显示 0 | `rollDay()` 只清今日，保留基线 |

> **为什么首次安装不从 0 开始补**：counter 是“开机以来”，可能包含昨天甚至前天的步数；
> 没有 Health Connect 的按日聚合时，任何“补算”都会虚高。宁可让用户从安装后开始。
> 若以后接 Health Connect，可用其 `StepsRecord` 的当日聚合值解决首次安装问题。

### 3.5 时区

`StepTracker.dayKey()` 使用 `ZoneId.systemDefault()`（手机本地时区）。跨时区旅行时，
“今天”按手机当前时区切换；电脑端 DB 的 `day` 按电脑本地日期，二者可能差一天。
当前协议没有定义时区字段，这是已知边界，文档中标注。

## 4. 前台服务与后台可靠性

### 4.1 为什么必须是前台服务

锁屏后普通后台进程会被 Doze/厂商冻结，传感器事件无法及时送达；而 counter 是累计值，
App 长期收不到事件就无法在零点/重启时正确拆分。前台服务是 Android 上持续计步的标准做法。

- Manifest：`android:foregroundServiceType="health"` + `FOREGROUND_SERVICE_HEALTH`；
- `startForeground()` 使用常驻通知（`IMPORTANCE_LOW`，不响铃）；
- 不申请 `WAKE_LOCK`：计步器是低功耗硬件传感器，靠系统批量上报即可；
- `START_STICKY`：被系统回收后尽量重建；
- `stopWithTask=false`：从最近任务划掉后仍继续（是否真被保留取决于厂商）。

### 4.2 Android 版本兼容

| 版本 | 关键点 | 处理 |
|---|---|---|
| 8.0–9 | 前台服务、通知渠道 | `NotificationChannel`（26+） |
| 10–12 | `ACTIVITY_RECOGNITION` 运行时权限；Android 12 后台启动 FGS 限制 | 首次使用请求权限；只在 Activity 前台/BOOT_COMPLETED 启动服务 |
| 13 | `POST_NOTIFICATIONS` 运行时权限 | 与计步权限一起请求；拒绝时仍可计步，但通知不可见 |
| 14 | FGS `health` 类型 + `FOREGROUND_SERVICE_HEALTH` | Manifest 声明；2 参数 `startForeground` 使用 manifest 类型 |
| 15+ | 更严格的后台限制 | 未在本环境验证；前台服务路径应仍可用 |

### 4.3 开机与兜底

- `BootReceiver`：`BOOT_COMPLETED` / `MY_PACKAGE_REPLACED`，仅当用户勾选“开机自启”、
  且已有 `ACTIVITY_RECOGNITION` 权限时启动；
- `SyncJobService`：`JobScheduler` 周期 15 分钟、`setPersisted(true)`、任意网络；
  不启动前台服务，只做一次 `SyncRunner.syncNow()`；
- 厂商 ROM 额外需要“自启动/后台运行”白名单；App 在首页/设置页给出入口与说明。

### 4.4 电池

- 传感器监听 `SENSOR_DELAY_NORMAL`；
- 同步间隔默认 5 分钟，早同步最小 75 秒；
- 通知更新节流 2.5 秒；
- 不持有 WakeLock、不做常驻轮询；
- 引导用户 `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`（侧载演示可接受；上架需评估政策）。

## 5. 同步设计

### 5.1 触发时机

| 触发 | 条件 | 备注 |
|---|---|---|
| 服务启动 | 5 秒后第一次 tick | 配置完整才发 |
| 周期 | `syncIntervalSec`（默认 300，可选 60/300/600） | tick 每 15 秒检查；上限 10 分钟，避免超过 15 分钟 stale |
| 步数推进 | 新增 ≥300 步且距上次尝试 ≥75 秒 | 让走路时数据更及时 |
| 手动 | 首页「立即同步」/ 通知按钮 | 不受间隔限制，但可能被后端 60s 去重 |
| 打开 App | 服务在跑、距上次尝试 ≥75 秒 | 顺手补一次，避免打开页面还看到旧数字 |
| Job | 15 分钟 | 前台服务被杀后的兜底 |
| 设置保存 | 启动服务后 5 秒 | 不立即写，避免用户刚填错地址就发 |

### 5.2 状态机

```
未配置 ──保存地址+令牌──► 待同步 ──成功──► 已同步 ──15min 无新上报──► 待同步(前端/首页)
                              │
                              ├── 401/400/网络错误 ──► 同步失败 ──下一轮重试──┐
                              └──────────────────────────────────────────────┘
```

`AppConfig` 记录：

| 字段 | 语义 |
|---|---|
| `last_sync_at` | 最近一次**成功**同步时刻（用于 15 分钟新鲜度） |
| `last_attempt_at` | 最近一次尝试时刻（用于间隔控制） |
| `last_sync_ok` | 最近一次是否成功 |
| `last_sync_msg` | 人话文案（含 HTTP 码/错误码） |
| `last_sync_code` | HTTP 状态码 |
| `last_synced_steps` | 最近一次上报的步数（用于 300 步早同步） |
| `last_sync_deduped` | 是否命中后端 60s 幂等 |

### 5.3 网络细节

- `HttpURLConnection`，连接 5s / 读取 8s；
- POST 只发一个很小的 JSON；**不使用 `setFixedLengthStreamingMode`**：
  JDK/Android 在 401 时会尝试“重试认证”，流式模式会抛 `HttpRetryException` 并丢掉
  `BAD_TOKEN` 响应体（这是联调时实际踩到的坑，已在 `SyncClient` 注释中记录）；
- 响应解析容忍未知字段；`{"ok":true,"deduped":true}` 视为成功；
- 网络异常/超时转成可读文案，写入状态，不崩溃、不阻塞传感器线程；
- 手动同步在 Activity 的后台单线程执行；服务同步在 `xiaoqi-step-sync` 线程；
- `SyncRunner` 用进程内锁串行化手动/Job；服务自身有 `AtomicBoolean` 防重入。

### 5.4 地址归一化

用户可能输入：

- `192.168.1.5:8000` → 补 `http://`；
- `http://192.168.1.5:8000/` → 去尾斜杠；
- 直接粘贴 `.../api/ingest/health` → 去掉已知接口后缀；
- `https://example.com/xiaoqi/` → 保留部署子路径；
- 非 http(s)、空主机 → 判非法，UI 提示。

## 6. 界面

### 6.1 首页

- 顶部：品牌 + 服务状态胶囊（未授权 / 未启动 / 计步中 / 无传感器）；
- 主卡：270° 渐变圆环 + 今日步数 + 目标百分比；圆环进度动画 900ms；
- 同步胶囊：已同步 / 待同步 / 同步失败 / 待配置；
- 两个主按钮：立即同步、设置；
- 条件横幅（只显示最需要处理的一条）：
  1. 缺少“身体活动”权限；
  2. 未配置地址/令牌；
  3. 后台计步未启动；
  4. 通知权限被关闭；
- 今日概览：目标、完成度、计步方式、后台服务；
- 同步卡：电脑地址、上次同步、同步结果、设备标识；
- 运行状态：权限、通知、电池优化 + 设置入口；
- 页脚：版本、接口、局域网说明。

### 6.2 设置

- 连接：地址、令牌、自动获取令牌、测试连接（只读）；
- 节奏：每日目标、同步间隔（1/5/10 分钟）、自动同步、开机自启；
- 权限与后台：状态 + 一键请求 + 电池优化；
- 演示与排障：+1000 步、今日清零（二次确认）、说明；
- 保存并启动 / 停止后台计步。

### 6.3 视觉

- 深色底 `#0F1318`，卡片 `#1A212A`，主绿 `#8BD97B`，暖白 `#F1F5F7`；
- 圆环自绘：轨道 + 渐变进度 + 端点圆点 + 60 格刻度；
- 全部文字走 `textContent`/`TextView`，不拼 HTML；
- 大字号数字 `sans-serif-light`，正文 `sans-serif`，中文回退系统字体；
- 所有可点控件有 `contentDescription` 或文本标签；圆环设置动态 `contentDescription`。

## 7. 协议映射

| 前端 `phone` 快照字段 | 来源 |
|---|---|
| `steps` | `StepRepository.todaySteps()` |
| `updated_ts` | 后端用请求 `ts` 或接收时间；App 发送当前 ms |
| `stale` | 后端 `PhoneIngest.stale()`；前端还会按 `updated_ts` 自行老化 |
| `source` | 请求体 `source=android-app`（当前 `PhoneIngest.snapshot()` 不暴露，但 DB/调试可见） |
| `device_id` | 请求体；后端用于 60s 幂等键 |

后端 `PhoneIngest.accept()` 的“只前进不回退”逻辑：若新 `steps` 小于已存值，视为跨零点/
系统重置，直接覆盖开新记录；否则取最大值。App 在零点把今日归零后，第一次上报的小值
正好触发这条规则。

## 8. 安全与隐私

- 只申请必要权限：计步、通知、前台服务、开机、网络、电池优化；
- 不读通讯录/位置/存储，不上传任何非步数数据；
- 令牌存应用私有 SharedPreferences，`allowBackup=false`（不随备份外泄）；
- 只允许局域网 HTTP（`usesCleartextTraffic=true`）；生产应改 HTTPS；
- 深链 `xiaoqi://pair` 会写配置，属于便利性 > 安全性的取舍；高安全场景应加签名/一次性码；
- 设备标识用 `ANDROID_ID` 加前缀，不采集 IMEI/MAC；
- 演示步数仅本地手动触发，默认不参与自动逻辑，不会伪造传感器事件。

## 10. 关键决策记录（本项目）

| # | 决策 | 理由 | 可逆性 |
|---|---|---|---|
| 1 | 只读消费 `backend/` 的协议，不修改后端/前端 | 避免影响现有姿态/房间链路 | — |
| 2 | 纯 Java + 无依赖 | 本机无 Gradle/网络，离线可编；APK 小 | 可换 Kotlin/AndroidX |
| 3 | 用 step counter 而非 Health Connect | 无依赖、全版本、实时；D-009 的步数子集 | 可换 Health Connect |
| 4 | 前台服务 + health 类型 | 锁屏持续、Android 14 合规 | 可换 WorkManager（但实时性下降） |
| 5 | 默认 5 分钟、早同步 75 秒 | 避开后端 60s 幂等；平衡及时性与耗电 | 可配置 1/5/10 分钟，上限 10 分钟 |
| 6 | 首次安装从 0 开始 | 避免把开机以来步数虚报为今天 | 可接 Health Connect 改善 |
| 7 | 失败保留文案，不自动清空 | 用户能判断是令牌/网络/配置问题 | — |
| 8 | 调试签名 | 无正式证书，课程演示足够 | 可换正式签名 |
